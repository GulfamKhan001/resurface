01Why this exists

The problem is not that you lack skill. It is that you have nothing you can show.

Your real work sits in two places, and neither can be pointed at. Mylo is private — 200+ backend modules, six production databases, reconciliation work that recovered ₹19.4M in misbooked payments, and none of it can be shown to a stranger. The job pipeline is public code you own, but you have ruled it out as a showcase, correctly: telling an employer you automated applications across nine job boards signals mass-applying, whatever the engineering quality.

So application forms ask "link us to something you have built" and the honest answer is currently nothing. That is the gap this project closes — and only that. It is not a business, not a startup, not a portfolio piece to be abandoned at 60%.

Your own objection, and the answer

You said: "only calling LLM API and getting response and showing to user is same as creating CRUD." You were right, and that objection is the design constraint for this whole project.

The answer: the LLM call is the cheapest, easiest part. The engineering exists because the operation being wrapped is slow (minutes, not milliseconds), expensive (real money per call), non-deterministic (the same input can give different output), and fails halfway through. CRUD is never any of those things. If this project ever degenerates into paste → call → render, it has failed and should be abandoned.

Everything in the phase plan exists to keep that from happening. The queue, the leases, the cost cascade, the resumability, the evals — each one is a thing you can only build because the wrapped operation is hostile.

02What it is

Save-it-and-actually-find-it.

You forward a link — a YouTube video, a podcast episode, an article, or an audio file. The system transcribes it, works out what is actually inside it (a recipe, a workout, a book recommendation, a place worth visiting), and stores that as structured, searchable data instead of another unread bookmark.

The one-sentence version for a recruiter who is not technical: "It turns the stuff you save and never watch into something you can actually search." That sentence is deliberately boring and deliberately understandable. The interesting part is underneath, and it only comes up when an engineer asks.

04How it works — architecture

Two runtimes, one database acting as the message broker.

The shape is dictated by one hard constraint and one deliberate choice.

The constraint: the free front door cannot do work

Cloudflare Workers is free, genuinely never sleeps, and handles 100,000 requests a day — but it allows 10 milliseconds of CPU per invocation. Waiting on the network does not count against it, so it can accept a request, write a row, and reply. It physically cannot transcribe audio. That forces a split between an always-on front door and an expensive back room, which is a real architectural pattern rather than an artifact of the free tier.

The choice: Postgres is the queue

No SQS, no Redis, no Kafka. SELECT … FOR UPDATE SKIP LOCKED with leases, visibility timeouts and per-user fairness, implemented by hand. A managed queue would hide every one of those mechanisms behind a configuration flag — and those mechanisms are the curriculum. You cannot claim to understand backpressure because you set maxReceiveCount in a console.

08The five engineering features

These are the reason the project is not a CRUD app. Each is a direct answer to an interview question.

FeatureWhat it actually doesThe question it answers
1 · Cost cascade Native captions (free) → RSS transcript (free) → paid ASR (last resort). A genuine runtime choice between a free and a paid path, with the cost recorded on the span. "How do you keep an AI feature from becoming a runaway bill?"
2 · Content-addressed dedup + singleflight Ten users saving one video produce one asset, one job, ten saves. A second request while a job is in flight attaches as a waiter rather than starting duplicate work — enforced by a partial unique index, not by check-then-insert. "Two identical requests arrive at the same instant. What happens?"
3 · Resumability chunks is a table, not a column. A worker that dies at chunk 7 of 12 resumes at 7 and does not re-spend on 1–6. Idempotency keys throughout. "Your worker dies mid-job. Do you pay twice?"
4 · Fair queueing Leases, visibility timeouts, backpressure, and per-user fairness. One person pasting 200 links cannot starve everyone else — expressed as ORDER BY in_flight ASC, with no rate limiter or quota table. "One tenant floods the queue. How do the others still get served?"
5 · Evals A golden set, schema-validated structured output, prompt-version regression runs, per-field confidence, and user corrections fed back as new eval cases. "How do you know the extraction is right?" — the one most people cannot answer.

The query you will be asked to walk through

WITH in_flight AS (
  SELECT fairness_user_id AS uid, COUNT(*) AS n FROM jobs
   WHERE state = 'leased' AND lease_expires_at > now() GROUP BY 1)
SELECT j.* FROM jobs j LEFT JOIN in_flight f ON f.uid = j.fairness_user_id
 WHERE j.state = 'queued' AND j.available_at <= now()
 ORDER BY COALESCE(f.n, 0) ASC, j.created_at ASC
   FOR UPDATE OF j SKIP LOCKED LIMIT 1;
Two details that will be probed

FOR UPDATE OF j, not a bare FOR UPDATE — Postgres refuses to lock "the nullable side of an outer join", and in_flight is LEFT JOINed. A bare FOR UPDATE fails at runtime with exactly that message.

SKIP LOCKED — without it, ten workers serialise behind a single row lock and throughput collapses to one job at a time regardless of how many workers you run.

09Phases 1–10, in depth

Each phase lists what you build, what you must understand before starting, and the gate you must pass to move on.

The rule that makes this work

Week 1 uses no AI at all. The worker sleeps and randomly throws. If you add transcription before the queue is provably correct, you will be debugging prompt quality and lease expiry at the same time and you will not know which is which. Earn the queue first.

WEEK 1–2

The queue, and breaking it on purpose

Schema, lease mechanics, and a chaos harness. The worker is deliberately terrible: it throws, it hangs past its lease, and it hard-exits mid-job. A separate test spawns real processes and kill -9s them while they hold leases.

  • enqueue with in-flight coalescing via the partial unique index
  • claim — the fairness query, SKIP LOCKED, a fresh lease token per attempt
  • heartbeat, complete (fenced on lease ownership), fail (backoff + jitter), reclaimExpired
  • A harness asserting: every job terminates; exactly one effect per job; zombie completions are rejected; poison dies instead of looping; the flooder does not starve anyone
Understand before you start
  1. At-least-once versus exactly-once. Exactly-once delivery does not exist. What you can have is at-least-once delivery with an effectively-once effect, which is why side_effects uses job_id as its primary key. Get this distinction wrong and every later design decision is confused.
  2. Why a lease is not a lock. A lock is held by a live connection and vanishes when it drops. A lease is a row with an expiry timestamp and survives the worker's death — which is precisely what makes recovery possible without any liveness detection.
  3. Fencing tokens. Lease expiry alone does not stop a stalled worker from completing, because its clock is not the database's clock. Read Kleppmann on fencing tokens; this is the subtlest idea in week 1 and the most likely to be probed.
  4. What SKIP LOCKED actually does — and what happens without it. Run the harness both ways and watch throughput collapse.
  5. Exponential backoff with jitter. Without jitter, a batch that failed together retries together forever, in lockstep, hammering whatever is already broken.
  6. Transaction isolation, enough of it. You need to know why the claim's SELECT and UPDATE must be in one transaction. You do not need to memorise all four isolation levels.

GATE — you can explain, without notes, why a worker whose lease expired must not be allowed to complete its job.

OutcomeA queue you trust because you broke it. This code is already written and typechecks; it has not yet been run against a live database.

WEEK 3–4

The real pipeline

Replace the fake worker with real stages: resolve the URL, run the cost cascade, transcribe in chunks with checkpoints, extract structured data with Claude.

  • Provider abstraction so the ASR vendor is swappable — you will want to compare at least two
  • Chunked transcription writing each chunk into chunks as it completes
  • Structured extraction with a schema, validated on the way out, not trusted
Understand before you start
  1. Streaming versus buffering large files. A two-hour podcast will not fit in memory on a small Cloud Run instance. Learn Node streams properly before this phase, not during it.
  2. Idempotency keys. Every external call that costs money needs one, or a retry becomes a double charge.
  3. Structured output from an LLM. Schema-constrained generation, and what to do when the model returns something almost-valid. Assume the JSON will be malformed sometimes and plan the recovery path.
  4. Timeouts and cancellation. AbortSignal throughout. An un-cancellable request is a lease you cannot honour.
  5. The difference between a retryable and a terminal error. Retrying a 400 forever is how a queue quietly stops making progress.

GATE — one real YouTube link goes in and correct structured data comes out, and killing the worker halfway does not re-spend on completed chunks.

OutcomeEnd-to-end on one real link, resumable.

WEEK 5

Observability, with money attached

OpenTelemetry across the edge, the queue and every worker stage, exported to Grafana Cloud. Cost recorded as a span attribute.

Understand before you start
  1. Traces, spans, and context propagation. The hard part is carrying trace context across a runtime boundary — from a Cloudflare Worker, through a database row, into a Cloud Run process. That is not a tutorial case and it is the thing worth having done.
  2. Spans versus metrics versus logs, and when each is the right instrument. Most people reach for logs for everything.
  3. Sampling. Trace everything and you will exceed the free tier and learn nothing. Head versus tail sampling, and why you always keep the errors.
  4. Cardinality. Putting a user ID in a metric label is how you accidentally create a million time series and get throttled.

GATE — you can open one trace and say where the time went and where the money went, without consulting the code.

OutcomeA trace that shows why one item cost more than another. Rare, and memorable to an interviewer.

WEEK 6

Real users, real contention

Telegram bot, dedup and singleflight under genuine concurrency, fairness verified under load. Give the link to friends.

Understand before you start
  1. Webhook security. Verify Telegram's signature. An unauthenticated webhook is an open door to your queue.
  2. Backpressure. What the system should do when it is already saturated — the correct answer is rarely "accept it anyway".
  3. The thundering herd. Ten simultaneous saves of the same trending video is the singleflight path's real test, and the only way to test it is concurrently.
  4. Rate limits as a first-class concern, both the ones you impose and the ones vendors impose on you.

GATE — a friend pastes 50 links and your own single link still completes promptly.

OutcomeSomething people actually use, which is a prerequisite for having real incidents to write about.

WEEK 7–8

Evals — proving the AI part is engineered

A golden set of 30–50 items with known-correct extractions. Schema validation, per-field confidence, prompt-version regression runs, and user corrections captured as new eval cases.

Understand before you start
  1. How to regression-test a non-deterministic system. The same input may legitimately produce different output. You need tolerant assertions and aggregate pass rates, not string equality.
  2. Precision and recall, applied to extraction. Missing a recipe ingredient and inventing one are different failures with different costs.
  3. Grounding and verification. Cross-check every extracted claim against the source transcript. This is your reconciliation instinct, pointed at a probabilistic system — the distinctive part of the whole project.
  4. Confidence calibration. A model's self-reported confidence is not probability. Learn what it is and is not good for before relying on it to gate anything.
  5. Prompt versioning. Treat a prompt as deployed code: version it, and re-run the golden set before shipping a change.

GATE — you change a prompt, run the suite, and can state what improved and what regressed, in numbers.

OutcomeA defensible answer to "how do you know it's right?", with data behind it.

WEEK 9–10

Ship it publicly and let it break

Public URL, README, and — the actual deliverable — written incident reports. Something will fail: a vendor will change an API, a queue will back up, a cost will surprise you. Write each one up: what broke, how you noticed, what it cost, what you changed.

This phase is the point, not padding

Verified research finding: what makes a project discussable is lived incidents narrated with ownership, resolution and a named cost — "battles won with losses" — not a flawless happy path. A self-inflicted outage on a zero-traffic demo does not have that property, which is exactly why week 6 exists to get real users first.

Understand before you start
  1. How to write an incident report that is neither defensive nor self-flagellating. Timeline, impact, root cause, fix, prevention.
  2. Alerting that is worth having. An alert you routinely ignore is worse than none, because it teaches you to ignore alerts.
  3. Secret hygiene and a public repo. Scan the history before you publish, not after.

GATE — three incidents written up. Each one is an interview answer you did not have before.

OutcomeThe interview material. This is what the previous eight weeks were for.

Why the cascade is the cost story
